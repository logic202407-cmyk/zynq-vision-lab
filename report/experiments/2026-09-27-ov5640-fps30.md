# OV5640 30 FPS timing trial on the vendor UDP baseline

## Scope and inputs

- Physical setup: the same XC7Z100-family board, ATK-MC5640 camera, GE/PL cable, 1 Gbps ASIX host adapter and `192.168.1.102:1234` receiver used for the [vendor video baseline](../../board/video_baseline.md).
- The original vendor HDL, IP files and bitstreams stayed outside this public repository under `D:/fpga-jtag-camera-test/`. Their redistribution rights have not been established. All JTAG programming was temporary PL configuration; Flash was not changed.
- Original vendor top-level timing parameters: `TOTAL_H_PIXEL=1856` and `TOTAL_V_PIXEL=984` for 640×480 RGB565. The vendor camera configuration comments state a 48 MHz pixel clock; `48 MHz / (1856 × 984) = 26.28 FPS` is an estimate from that configuration, consistent with the measured 26.28 FPS baseline, not an independent clock measurement.
- Trials copied the local vendor RTL, two XCI files and XDC into separate ASCII-only directories. Vivado 2024.2 upgraded Clocking Wizard 6.0 revision 12 to 15 and FIFO Generator 13.2 revision 8 to 11 in each isolated project. The physical package/speed grade remains unconfirmed by direct chip marking; builds used the vendor project's `xc7z100ffg900-2` target.

The horizontal trial delivered about 14% more complete frames over 300 s than the separate original-vendor 300 s run (8999 versus 7884). The theoretical rate from the vendor's 48 MHz comment is `48 MHz / (1626 × 984) = 30.0003 FPS`; this is only a consistency check. A single 640×480 frame from the horizontal trial was decoded with the PC viewer's RGB565 conversion and visually inspected: the real room scene and red paper square were recognizable. The private image is retained only outside Git. The live Tk viewer was relaunched and bound to UDP port 1234 after the headless run; its display FPS could not be read from a desktop screenshot while Windows was locked.

## Evidence and limits

- Local JSON summaries (outside Git): `fps30_trial_2026-09-27/baseline_before_trial.json` SHA-256 `3f225ff82c42c6a26032a05aeae852e36d4042d25ae3b49134d1c003e31cc796`; `fps30_trial_2026-09-27/trial_probe_30s.json` SHA-256 `79a58ea950f843d54a220c2e546ca01ef0e8e3ae06a9bc67b1c353723b32a77e`; `fps30_control_2026-09-27/control_probe_10s.json` SHA-256 `99bf158855802e0ec5e159c927a66500c6aa1ad89875e822526d7606f9ea4e6e`; `fps30_horizontal_2026-09-27/horizontal_probe_300s.json` SHA-256 `1657108a11a11983739bed9bae3408698afdadbd5945b4cdaf27fedf73f32a77`.
- The horizontal trial's final Vivado report gave WNS 3.049 ns and WHS 0.108 ns on **constrained** paths; bitstream-generation DRC found 0 errors. The inherited vendor timing methodology still reports 90 non-clocked sequential pins, 227 unconstrained internal endpoints, and missing input/output delays. Thus this is not complete I/O timing closure.
- The UDP format has no frame ID, row index or row CRC. Zero incomplete frames does not rule out silent row duplication, reordering or pixel errors. Only one frame was visually inspected; exposure, motion blur, color accuracy, and reproducibility after power cycling remain unmeasured. A second person has not rebuilt or reproduced the trial.
- These measurements concern the vendor camera-to-UDP path. The self-written red-pixel PL module is not integrated here and its board performance is still unverified.

## Reproduction boundary

Use a licensed local copy of the vendor `50_ov5640_udp_pc` project. Build the original timing as a control under the same Vivado/IP revisions, then change only the top-level horizontal total from 1856 to 1626 while keeping 640×480 and vertical total 984. Record source diff, IP upgrade status, implementation/DRC/timing reports, bitstream hash, JTAG startup, and a timed UDP probe. Do not publish copied vendor HDL, XCI, XDC, bitstreams, camera images or license files. Preserve the original vendor bitstream as a rollback if frame headers or image quality regress.
