# 基于 Zynq 的几何靶标视觉感知与动态干扰实验平台

## 项目规划 v0.1

编制日期：2026-09-18（北京时间）；公开仓库版 v0.1.1  
对应方向：全国大学生嵌入式芯片与系统设计竞赛，AMD 3.3 自主选题赛道初级组。  
当前状态：完成资料调研与方案规划；没有据此宣称任何代码已实现、仿真已通过或硬件已验收。  
引用说明：[S01]—[S12] 的出处、适用范围和核实限制见 `sources.md`。

## 1. 决策摘要

项目保留“真实靶标、实时视觉、动态场景、光学交互”的直观展示思路。首轮交付以封闭实验区域中的圆形、彩色或编号纸质靶标为对象，以屏幕中的目标标记、轨迹和量化测量作为主要验收输出。实体光学交互作为经过指导教师和场地安全审核的独立演示项，不把自动化人员/飞行器指向、移动发射平台或多光束协同作为本期研发内容。

技术主线定为：**现有板卡及工具链核实 → 原厂视频链路 → 自编 PL 图像处理 → 单目标测量 → 可区分的多目标 → 环境干扰实验 → 可选移动相机实验。**

不要同时启动三路光学机构、通用多目标追踪、大模型部署、PYNQ 移植和移动底盘。每一项都必须在前一个可独立演示的版本通过后再开启。

创新表达不使用“首次实现视觉自动跟踪”。2023 年电赛已有“运动目标控制与自动追踪系统”题目。[S12] 本项目拟验证的差异是：让 FPGA 承担实际图像计算，给出公平的软硬件对照，在重复的干扰场景中测量性能变化，并提供可复用验证工具。它们是拟实现的工程贡献，不是已经证明的原创成果。

## 4. 系统边界与阶段功能

### 4.1 首期必交付：可复现的板级视觉测量系统

输入为实际可用摄像头的视频，输出为目标区域、目标中心、有效/丢失状态、帧编号和实测性能信息。至少一段有实际运算价值的图像处理必须由团队编写并在 PL 中运行，而不是只把原厂摄像头例程运行一次。

完成标志：另一个成员能从指定提交版本重新构建并上板，在约定场景中重复得到输出。

### 4.2 版本分层

| 版本 | 功能范围 | 进入条件 | 明确不承诺 |
|---|---|---|---|
| V0 链路基线 | 原厂视频、显示/日志、帧计数 | 板卡、电源、工具链、下载链路已核验 | 不称为自研算法或最终作品 |
| V1 最小完整系统 | 单个几何靶；PL 实际处理；目标标记与位置测量；无目标时输出无效；保存数据 | V0 可重复启动 | 不承诺通用物体识别、复杂遮挡或高速追踪 |
| V2 主展示版本 | 2—3 个可区分的几何靶；目标移动；光照/背景/遮挡实验；性能对照 | V1 板测通过、核心时序问题已解决 | 不把不同颜色的识别等同于任意同类多目标追踪 |
| V3 可选扩展 | 相机缓慢移动时的观测实验，或轻量图案分类 | V2 已完整交付且距离功能冻结仍有余量 | 不同时增加复杂运动、AI 部署和多实体光束 |

实体光学交互不作为视觉算法开发的前置依赖。未完成安全审核时，继续用屏幕叠加完成全部识别与动态实验，不因此堵塞 FPGA 主线。

### 4.3 安全范围

实验对象限定为无生命、几何化的标靶；没有实弹、弹丸或破坏性输出，不以真人或真实飞行器为自主指向对象。真实光学设备由指导教师审核类别、封闭光路、终止屏、独立停机与操作流程，未经审核不启动发射。

“可见光”或“低功率”不自动意味着安全。FDA 的激光危害说明中，部分可见激光类别仍有直接观看造成眼损伤的风险。[S11] 该来源只用于说明一般光学风险，不作为中国场地法规的替代。

## 5. 技术路线选择

### 5.1 默认路线：原厂可复现工程 + 小型自编 PL 模块

优先找到与确切板卡、摄像头和工具版本匹配的原厂例程，保留其已验证的采集与显示框架。在此基础上插入一个职责单一的自编模块，并先以固定测试图像与黄金参考验证。

本期不要求从零重写 DDR、完整相机驱动和显示控制器。复用现成接口并不取消团队的原创贡献；需把自编模块、复用模块及修改部分标清。

### 5.2 PYNQ 是条件分支，不是先决条件

AMD 指南推荐初级组使用 PYNQ，但没有强制要求。[S02] 官方 PYNQ 文档区分“已有匹配镜像的板卡”和“需要构建镜像的新板卡”；后者还涉及启动文件、内核、设备树与文件系统。[S05]

决策规则：首个有效开发日内，确认是否有与确切硬件匹配且可验证的镜像/Overlay。存在则评估采用；不存在则沿原厂软件栈推进，不为额外加分先投入一周移植。不能把 PYNQ-Z2 的镜像和引脚当作任意 Zynq 板都适用。

### 5.3 工具版本必须成套固定

上传指南推荐 Vivado/Vitis 2026.1 或 2025.2，也允许其他版本，但要求说明并可复现。[S02] 2026.1 的器件分级表将 Zynq-7000 全系列列入 Basic 档，而新版又引入了启动前许可证文件要求；不能沿用旧版免费器件清单直接作结论。[S03][S04]

版本选择由“原厂项目能否重建、目标器件/IP 是否可用、同版本工具是否配套”共同决定，不以“越新越好”为原则。第 1—2 个有效开发日就要完成一次最小工程生成位流并下载，而不是只安装软件或打开项目。

### 5.4 RTL 与 HLS 的分工

建议以少量 RTL 建立时钟、复位、流水线、有效信号、寄存器和状态机的基本认识。图像算子可选 RTL 或 HLS，依据团队实际实现与验证成本决定。

AMD XUP HLS 教程涵盖仿真、综合、优化、IP 导出与集成，并提供 Sobel、卷积等项目，但教程针对列明的开发板和工具年代，不代表目标板卡可直接运行。[S07]

Vitis Vision 的 L1 示例适合学习单算子的 C 仿真、综合、联合仿真与 RTL IP 导出；不要一开始照搬面向其他开发平台的 L2/L3 完整系统。检索时主分支 README 对应 2026.1，必须选择与本地工具匹配的版本。[S06]

### 5.5 高层数据流

摄像头/已标明来源的测试视频 → 采集接口 → PL 图像处理与统计 → PS 读取结果及状态管理 → 屏幕标记、实验记录和性能展示。

显示图像可走原厂已验证的缓存/输出路径。第一版不为“全系统都必须流式”而改写所有接口。

| 位置 | 首期职责 | 验收证据 |
|---|---|---|
| PL | 基础像素处理、目标区域统计、帧/事件计数、必要的寄存器接口 | 自检仿真、综合/实现报告、板测输出 |
| PS | 读取一致的结果快照、目标有效性/编号、日志与显示组织 | 帧编号对齐、异常状态日志、重复运行记录 |
| PC | 黄金参考、数据标注、结果比较、构建与汇总 | 同一输入的参考结果和比对文件 |
| 实验装置 | 提供可重复的目标位置/移动/遮挡/照明场景 | 场景照片、实验配置、重复实验编号 |

PC 可以参与开发和验证；正式展示时必须说明它到底在做显示、日志还是算法，不能把 PC 检测结果隐藏在“FPGA 识别”的叙述中。

## 6. 多目标、动态场景与 AI 的边界

### 6.1 多目标不是简单复制单目标代码

多个不同颜色/编号的几何靶、多块相同颜色的靶、发生交叉遮挡的同类靶，是三种不同难度的需求。V2 先支持可区分靶标，形成明确可复现的任务；不能用整体前景的一个中心值宣称同时识别了多个目标。

完全遮挡时目标位置本身不可直接观测。验收要求是诚实输出“不可见/丢失”，并在重新可见时恢复测量，不要求凭空证明始终没有身份交换。

### 6.2 移动目标与移动相机分开验证

先在固定相机下改变标靶状态，再做相机运动实验。不要把“目标移动、相机移动、背景变化”同时引入第一次联调。

移动相机的首期扩展是受控实验条件，不是要求同时开发自主行驶底盘。IMU/编码器有可验证的实际需求后再考虑，不预先把多传感器融合写成必须交付的创新点。

### 6.3 AI 的两条独立路径

开发协作路径是必做记录：用模型辅助理解模块、生成候选测试、解释错误和审查结果；所有结果经过本地工具及实物核验。这服务于赛事的协作与技能包要求。[S02]

设备推理路径是可选功能：在传统视觉已稳定后，用小型图案分类实验检查能否减少相似背景的误识别。先做离线基线与测试，再决定是否部署到 PS 或 PL；模型训练完成不等于板端推理完成。最终报告写清推理位置、版本、数据划分和实际帧率。

不把大模型、YOLO、大型模型量化和专用加速器同时加入首轮计划。轻量 AI 没有证明增益时就不作为主卖点。

## 7. 量化验收与对比方法

以下数字均为建议的内部目标，不是赛事硬性要求，也不是已实现性能。确认硬件后允许调整，但需在正式测试前冻结版本与阈值。

| 项目 | 暂定目标或规则 | 如何验证 |
|---|---|---|
| 视频规格 | 优先评估 640×480、30 帧/秒；以摄像头与接口实际支持模式为准 | 记录实际帧到达计数，不只读取配置值 |
| 目标数量 | V1 为 1 个，V2 为 2—3 个可区分靶标 | 对照场景清单与独立标注 |
| 像素算子正确性 | 整数算子与约定黄金参考逐像素一致；存在舍入时提前声明容差 | 同一测试图、像素布局、边界定义与结果文件 |
| 定位评估 | 报告可见帧的位置误差中位数和 95 分位；也按目标尺寸归一化 | 与人工/独立参考标注比较，说明参考误差 |
| 检出与误识别 | 分别报告检出率、误检次数和无目标场景错误输出 | 固定匹配规则；不能只测有目标视频 |
| 连续运行 | 先以连续 10 分钟不崩溃为内部目标 | 保存完整日志、输入帧数、输出帧数、丢帧计数 |
| 可重复启动 | 3 次断电重启后按同一流程恢复工作 | 每次单独记录启动与运行结果 |
| 性能 | 同输入同算法条件下，比较软件基线与 PL 路径 | 标明搬运、缓存、预处理、显示是否计入 |
| FPGA 工程 | 检查实现后时序、约束完整性、跨时钟域处理、资源占用 | 保存报告；没有负裕量不代表漏约束路径也正确 |
| 复现 | 第二名成员在干净目录按说明重建并运行 | 记录提交版本、工具版本、文件校验和与输出 |

关键口径：

- 图像处理算子延迟、从帧输入到目标坐标产生的延迟、摄像头到屏幕的端到端延迟分别报告。不要把它们混为一个“系统延迟”。
- 电脑 Python 运行时间可以作为软件参考数据，但不能直接据此宣称 FPGA 比 Zynq PS 快多少；公平加速比应尽量比较相同输入、相同任务和明确边界。
- 每周期接收一个像素的流水线仍受输入帧率、行/帧等待、缓存和后处理影响；不据此推算整机达到微秒级响应。
- 对重计算类、全帧统计类和接口开销分别测量；不把 CPU 描述成只能串行而 FPGA 自动没有瓶颈。
- 界面中未测的值显示“未测”，不要填入示例 60 FPS、8.4 ms 或 1—2 像素误差。

### 建议的六类场景

S0：干净背景、静止靶；S1：移动靶；S2：照明变化；S3：相似背景；S4：部分遮挡与短时消失；S5：受控相机移动（仅可选扩展）。

每种已开启场景先采集 3 段 30 秒测试素材并完整保留。单变量测试完成后，再组合两种干扰。没有照度计时记录灯具、档位和位置，不编造 lux；遮挡比例不能精确测量时标注为估计值。

训练、调参和最终测试按不同拍摄批次/完整视频划分，避免把同一段视频的相邻帧分别放入训练集和测试集。先确定评价规则，再看最终成绩。

| 11-02—11-04 | 上传和修正缓冲 | 不在最后一天升级工具或更换硬件 |

有实际课程冲突时调减功能，不通过减少验证和睡眠把 30 天变成“理论足够”。

## 9. 三人分工与学习安排

本次报名名单以实际审核结果为准，不在公开仓库记录私人报名材料。按当前规则，由队长确定实际 3 人名单和角色。[S01]

| 角色 | 主责 | 必须了解的共同部分 |
|---|---|---|
| 队长（建议队长承担） | 范围决策、PL 基础与集成、版本合并、答辩技术主线 | 每个接口的来源/去向，当前瓶颈，如何验证 |
| 成员 B | 软件参考、数据采集/标注、PS 结果组织与显示 | 自编算法的数学含义、数据格式与测量边界 |
| 成员 C | 物理实验台、接线/供电核验、测试执行、复现及材料 | 启动流程、异常状态、最小 FPGA 工程 |

代码作者与验证者尽量不是同一人。每个模块都有一名负责人、一名复核人，禁止“谁有空谁改主工程”。

每天建议保留 30—45 分钟共同 FPGA 基础训练，约每周一次不依赖 AI 现写现测：组合/时序逻辑、计数器、状态机、复位、有效信号、简单接口及 testbench。HLS 路线也不取消这些训练；决赛基础考核有单独要求。[S01]

学习顺序与工作包绑定，不采用“先看完一整套课程再开始”的方式。必须能够解释：仿真波形意味着什么、为什么要约束时钟、跨域数据何时可信，以及综合成功与板上正确有什么不同。

## 10. GitHub Skill 的实际使用方式

本次已阅读 `obra/superpowers` 的三个 Skill 原文，作为规划与验证方法参考，没有安装插件或执行仓库脚本。[S08][S09][S10]

| Skill | 借鉴的方法 | 本项目中的具体落点 |
|---|---|---|
| writing-plans | 任务有边界、接口、独立可验证产物 | 每个工作包写清输入、输出、文件与验收；详见 `first_week_tasks.md` |
| systematic-debugging | 先找可复现根因，一次验证一个假设 | 黑屏按采集/同步/PL/缓存/显示逐段收集证据，不反复盲改 |
| verification-before-completion | 无新鲜证据不宣称完成 | 区分已编写、仿真通过、实现通过、板测通过、独立复现 |

这些 Skill 不是可综合 IP，不会解决板级引脚和时序约束，也不能替代设计报告中的本人理解。

### 拟沉淀的原创技能包

优先选择一种并做实，不追求文件数量：

- 图像黄金参考比对：输入格式、边界定义、结果容差、失败样例和报告生成说明；
- FPGA 工程证据核验：区分仿真、时序、板测结果，校验版本与结果对应关系；
- 视频链路排错：每段接口可观察信号、现象、假设、验证步骤及复发测试。

目前它们仅是候选，不能在报告中写成“已验证通用技能”。只有陌生模块/不同测试数据上的复用得到证据后，才增加适用范围；没有换板验证就不要写“支持任意开发板”。

## 11. 仓库组织、证据与开源

建议源码仓库建立 `src/rtl`、`src/hls`、`src/ps`、`sim`、`build`、`board`、`data`、`skill`、`report`。目录与文件名使用纯英文，文档正文可中文；这是上传指南明确强调的复现要求。[S02]

每次可演示版本至少保存：提交号、工具/IP/板卡版本、输入数据校验和、关键配置、仿真输出、实现报告、板测记录与失败案例。生成文件和源文件分清，不能只交一个无法重建的 `.bit`。

第三方代码记录上游链接、commit/tag、许可和具体修改。没有许可或许可不清晰的工程，不直接复制并统一改成 MIT；先换用许可明确的材料，或只借鉴公开原理。原厂资源是否允许公开再分发也需要确认。

从模型获得的代码同样经过本地编译和实测；记录有代表性的错误、修复依据和失败边界，不为凑篇幅倾倒所有无关聊天。

## 12. 风险与退出条件

| 风险 | 早期信号 | 处理原则 |
|---|---|---|
| 板卡型号不清 | 原厂工程 part 与板卡标签不一致 | 暂停引脚和资源方案，先确认硬件 |
| 工具/许可 | 只能打开项目，不能实现或生成位流 | 在最小工程解决，不拖到算法完成以后 |
| 视频链路 | 连续 3 个有效开发日没有稳定画面 | 独立做测试图的板级处理；排查并保留原厂可用链路，不掩饰输入来源 |
| 自编核心迟迟不上板 | 10-05 仍只有软件算法 | 删除 AI、相机移动等扩展，集中完成 PL 闭环验证 |
| 多目标范围膨胀 | 开始同时解决同色交叉、遮挡、运动、分类 | 回到可区分标靶任务；剩余列为已知限制 |
| 光学演示未审核 | 封闭条件/发射类别/场地流程不明确 | 不发射，使用屏幕标记；不影响视觉与实验主线 |
| 指标漂亮但不可信 | 无原始输入、没有失败样例、软件与硬件测量范围不同 | 重做测量，不用推测值补表 |
| 最后两周仍堆功能 | 稳定版本丢失、工具频繁更换 | 冻结功能，仅修关键缺陷并准备提交 |

## 13. 第一轮交付清单

技术交付：可重建工程、实际运行的自编 PL 模块、板测输出和参考比对。  
实验交付：条件明确的测试集、干扰实验、真实性能与误差统计、失败边界。  
演示交付：从断电启动到运行的完整流程、实时界面与保底演示素材。  
赛事交付：报告、视频、资源/时序报告、AI 协作记录、经过验证的技能包、开源来源与复现说明；最终格式以届时官方提交要求为准。[S02]
